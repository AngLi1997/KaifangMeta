# 统一权限组件

> SDK 组件，平台控制台与业务系统共用；控制台数据由认证模块托管。相关：[统一认证与身份](identity.md)、[SDK](../../sdk.md)。

## 要点

- **一套组件，多份数据**：SDK 提供可配置的 RBAC 组件（权限点、菜单、角色、带作用范围的角色绑定），平台控制台与业务系统共用同一套实现，权限数据各自存在本系统的库或 schema 中，运行时不依赖中心授权服务；特殊权限体系的业务系统可自行实现。
- **平台控制台视为内置应用** `kaifang-meta-console`：是统一权限组件的第一个使用方，权限数据存于平台 `console_authz` schema（认证模块托管，与身份表隔离，仅按 `sub` 关联）。内置超管、租户管理员、应用管理员、能力负责人、审计员等角色，支持自建角色与自定义菜单。权限点在代码中声明并经权限清单注册，角色、菜单、绑定均可配置；组件内置防越权授予规则。


## 结论：一套组件，多份数据

授权原则不变：认证模块只管身份，**谁使用就由谁维护授权**。平台控制台也按这一原则处理，作为内置应用 `kaifang-meta-console` 接入认证模块，与业务系统地位相同。

平台和业务系统**不各做一套权限系统**，也**不建中心化授权服务**，而是共用 SDK 中的统一权限组件（RBAC 组件）：

| 方案 | 问题 | 结论 |
|------|------|------|
| 平台、业务各做一套 | 模型、界面、审计做两遍，规则逐渐不一致 | 不采用 |
| 平台统一授权中心 | 违背“业务权限归业务系统”；业务运行时强依赖平台；平台不理解业务数据范围 | 不采用 |
| **一套组件，多份数据** | 需要把作用范围抽象得足够通用 | **采用** |

- **一套**：模型、代码（Java / Python）、管理界面只有一份，随 SDK 发布。
- **多份数据**：每个使用方把权限数据存在自己的库或 schema 中，运行时不调用任何中心服务。
- 平台控制台是该组件的**第一个使用方**，数据存于平台 `console_authz` schema（由认证模块托管，与身份表逻辑隔离、互不引用，仅按 `sub` 关联）。
- 有特殊权限体系的业务系统可以不用该组件，自行实现。

## 数据模型

```
权限点 permission   代码声明，经权限清单注册（如 capability:publish）
菜单 menu           可配置的树，节点挂权限点
角色 role           可配置，权限点的集合；分内置角色与自定义角色
作用范围 scope      类型由使用方注册，实例为 (scope_type, scope_id)
角色绑定 binding    (sub, role, scope_type, scope_id, 生效期, 授予人)
```

**代码固定与可配置的边界**：

| 对象 | 维护方式 | 原因 |
|------|---------|------|
| 权限点 | 代码声明 + 权限清单 | 接口靠它做校验，代码不检查的权限点配了也无效 |
| 菜单 | 可配置（清单提供默认菜单树） | 菜单结构、名称、顺序可按单位调整 |
| 角色 | 可配置（内置角色 + 自定义角色） | 不同单位分工不同 |
| 角色绑定 | 可配置 | 日常授权操作 |

## 权限清单

每个使用方随代码发布一份权限清单，组件启动时同步到本系统的权限表：

```yaml
# kaifang-meta-console.permissions.yaml
app: kaifang-meta-console
scopes: [system, tenant, app, resource]
permissions:
  - code: capability:publish
    name: 发布能力版本
    scopes: [system, resource]         # 具体能力作为一种资源类型
  - code: annotation:manage
    name: 标注模板与工单管理
    scopes: [tenant]
  - code: annotation:work
    name: 我的标注（领取任务池、自由标注）
    scopes: [tenant]
menus:
  - code: caps
    name: 能力目录
    permission: capability:view
roles:                                 # 内置角色，不可删除
  - code: tenant-admin
    name: 租户管理员
    scope: tenant
    permissions: [tenant:*, app:view, annotation:*]
```

- 清单中新增的权限点自动注册；删除的权限点标记为**失效**而非物理删除，已绑定的角色在管理界面提示清理。
- 内置角色的权限集随清单升级；管理员可在内置角色之上**追加**权限点，但不能移除清单声明的部分。

## 作用范围

平台和业务系统的授权本质上都是“角色 + 作用范围”，区别只在作用范围的类型：

| 使用方 | 作用范围类型 | 示例 |
|--------|------------|------|
| 平台控制台 | `system`、`tenant`、`app`、`resource` | 租户管理员 @ `tenant:t_001`；应用管理员 @ `app:t_001/kaifang-meta-archive-room`；能力负责人 @ `resource:capability:c_001` |
| 智慧档案室 | `org`、`dept`、`fonds`（全宗） | 档案员 @ `dept:d_12` |

- 作用范围类型由使用方注册，并提供**层级解析**接口（如 `tenant` 包含其下的 `app`；`org` 包含其下的 `dept`），组件据此判断上级范围的授权是否覆盖下级。
- 数据范围过滤（SQL 条件）仍由业务代码根据 `scopes_of(sub, permission)` 的结果拼装，组件不理解业务表结构。

### 平台数据范围规则

平台控制台的数据授权使用以下层次，不按机构树授权：

| 范围 | 标识 | 覆盖内容 | 典型授权 |
|------|------|----------|----------|
| `system` | 固定 ID `t_system` | 全局平台配置与跨租户运维 | 平台超级管理员、全局审计员 |
| `tenant` | `tenant_id` | 单租户内的平台配置、任务与用量 | 租户管理员 |
| `app` | `tenant_id + client_id` | 某租户下单个应用及其关联配置 | 应用管理员 |
| `resource` | `resource_type:resource_id` | 具体能力、任务、标注项目等对象 | 资源负责人或被委派成员 |

授权按请求顺序校验：

1. 从已验签身份取得 `sub` 与 `tenant_id`；Token 不携带角色或权限。
2. 校验操作权限点，例如 `capability:publish` 或 `annotation:manage`。
3. 解析用户在目标作用范围内的角色绑定；父范围只有在该类型明确声明层级关系时才能覆盖子范围。
4. 资源所属模块再按资源的 `tenant_id`、`client_id`、资源 ID 或成员关系生成查询条件；无匹配范围时拒绝访问，不返回未过滤的数据。

平台业务表应带租户归属；应用私有配置还应记录 `client_id`。资源记录通过自身 ID 或明确的父资源字段归属到租户 / 应用。全局目录可由平台范围访问，但租户绑定、调用记录、任务结果等数据必须在查询时应用租户与应用范围。跨租户操作只允许持有 `system` 范围权限的角色。

机构主数据由平台维护（见 [统一认证与身份 · 机构](identity.md#机构)），业务按机构 `id` / `code` 定义 `dept` 等数据范围；`fonds` 等业务专有范围由业务系统注册并解释层级，权限组件只处理不透明的作用范围 ID。运维团队如需相互隔离，应建平台成员组或资源授权关系，并映射到上述 scope，不复用业务部门树。

### 当前仓库实现边界

当前控制台落地了 `system` / `tenant` 两级作用范围，`app`、`resource` 范围、层级解析与按权限点子集的授予校验仍是目标设计：

| 环节 | 实现 |
|------|------|
| 角色 | `console_authz.role.scope`：`system`（如「管理员」）只在系统租户生效；`tenant`（如「租户管理员」「普通用户」）在绑定的租户内生效 |
| 绑定 | `console_authz.role_binding`（成员 × 角色 × 租户）；`DependPermission`、用户菜单与按钮权限只取 Token `tid` 内的绑定；`is_superuser` 只在系统租户生效 |
| 数据过滤 | 控制台接口按 Token `tid` 注入条件：业务租户只看本租户的账号、成员角色、审计日志与租户信息；新建租户、修改租户、跨租户成员只允许系统租户 |
| 防越权 | 系统角色只能绑定在系统租户；业务租户只能在本租户授予 `tenant` 角色，且不能授予或移除「租户管理员」 |
| RLS 兜底 | 见 [网关与鉴权](../../gateway.md)「轻租户」 |

新增租户或应用数据的平台模块，表必须带 `tenant_id`（应用私有配置再带 `client_id`），查询按 `tid` 注入条件并为该表启用 RLS；不能把 API 权限校验误当成数据权限。

## 平台控制台的内置角色

| 角色 | 作用范围 | 授予人 | 说明 |
|------|---------|--------|------|
| 平台超级管理员 | `system`（`t_system`） | 初始化 / 其他超管 | 管理所有租户与全局配置 |
| 租户管理员 | `tenant` | 超管 | 管理本租户的应用开通、成员与角色 |
| 应用管理员 | `app`（应用空间） | 平台管理员（应用接入时指定） | 自助管理本空间资源，见 [能力目录](../capability/catalog.md) |
| 能力负责人 | `resource`（资源类型 `capability`） | 超管 / 租户管理员 | 审批受限能力、发布版本 |
| 审计员 | `system` 或 `tenant` | 超管 | 只读，查看审计日志与计量 |
| 标注员 | `tenant` | 租户管理员 | `annotation:work`：控制台「我的标注」、领取任务池、创建自由标注 |

在内置角色之外，租户管理员可以在本租户内自建角色（如“标注管理员”），并自定义菜单。工单内的标注员、质检员是标注工单成员（平台身份账号 `sub`），由发起方指定；从业务系统打开工作台只看成员身份，只有要进入控制台「我的标注」或自建自由标注时才需要「标注员」角色，见 [数据标注](../annotation/overview.md)。

## 防越权授予

组件内置以下规则，平台和业务系统同样适用：

1. **只能授出自己持有的权限点**：自建角色或绑定角色时，所含权限点必须是操作者在该作用范围上持有的子集。
2. **只能在自己的作用范围内授予**：租户管理员只能在本租户及其下级范围内绑定角色。
3. **内置管理角色不可自授**：超管、租户管理员角色的绑定须由上级授予，不能给自己或同级授予。
4. 所有角色变更、绑定变更写入审计日志（操作者、目标 `sub`、前后差异）。

## 运行时与模块边界

- **鉴权链路**：网关只校验 Token 的 `aud`（控制台为 `kaifang-meta-console`）；控制台接口层调用 `authz.check(sub, permission, scope)`；资源级判断在所属模块内完成，例如能力模块判断是否为该应用空间的管理员，标注模块判断是否为工单成员（从业务系统打开的标注工作台不要求控制台角色）。
- **模块间**：平台各模块通过授权接口查询，不跨 schema 读 `console_authz` 表，符合“模块间只走接口”的约束。
- **缓存与失效**：组件按 `sub` 缓存权限计算结果（默认 5 分钟），绑定变更时主动失效；收到 `user.disabled` 事件时清理该 `sub` 的全部绑定缓存。
- **Token 不携带角色或权限**，避免授权变更需等待 Token 过期。

## 初始化与应急

- 第一个平台超级管理员在部署时由 kaifang-meta-operator 或部署配置写入 `console_authz`。
- 保留一个本地应急账号（不经企业 IdP），用于 IdP 不可用时登录控制台；该账号默认禁用，启用与每次登录均告警并审计。

## 交付形态

| 部分 | 形态 | 说明 |
|------|------|------|
| 后端 | `kaifang-meta-sdk` / `kaifang-meta-spring-boot-starter` 内的 RBAC 组件 | 建表脚本、清单同步、`check` / `scopes_of` 接口、注解（如 `@KmPermission("capability:publish")`） |
| 前端 | `kaifang-meta-shell` 内的权限管理页面 | 角色、菜单、绑定、审计四个页面；菜单按权限渲染 |
| 数据 | 使用方自己的库或 schema | 平台为 `console_authz`，业务系统为本业务库 |

**可选的托管模式（后续再做）**：不想维护权限界面的小系统，可把权限数据交给平台控制台代管。数据仍按应用隔离，业务系统运行时经 SDK 拉取并缓存，不强依赖平台在线。默认仍由各系统自存。
